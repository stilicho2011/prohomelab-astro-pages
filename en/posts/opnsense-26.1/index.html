    Introduction

    Let's dig into setting up OPNsense 26.1, that gateway/firewall you've probably already heard of.

    Note

    This is, as far as I know, the only guide of its kind in Russian - it took a genuinely absurd amount of time and effort to put together. If it helps you out and you feel like buying the author a coffee, there's a Boosty link for that.

    My site already has a fair amount of OPNsense content scattered around, but for anyone just starting out it's all over the place and hard to stitch together into a coherent picture. So, mustering whatever willpower I had left, I finally sat down to write this thing - my own little Sisyphean task.

    What OPNsense Actually Is

    OPNsense is a free, open-source firewall/router distro built on top of FreeBSD. It turns a regular PC, a mini-PC, or even a VM into a full-blown, enterprise-grade network appliance.

    People tend to call it "just a firewall," but that undersells it quite a bit. On top of filtering traffic, it can moonlight as a router, VPN gateway, DHCP/DNS server, load balancer, reverse proxy, IDS/IPS - basically a one-stop shop for network security.

    Note

    A few features, like the reverse proxy, need a plugin installed first.

    One of the best things about OPNsense is that it packs all this functionality behind a genuinely usable web UI, with regular updates on top. You can get almost everything done through the GUI - no need to live in a terminal.

    How OPNsense Stacks Up Against the Alternatives

    The usual suspects you'll be comparing it to are pfSense, MikroTik RouterOS, OpenWrt, and the classic "hand-rolled Linux box acting as a router."

    What sets OPNsense apart is its focus on ease of administration, a transparent development process, and a steady stream of updates. It started life as a pfSense fork (which is itself a fork), and from day one it leaned hard into open development, a modern management UI, and a release cycle you can actually plan around.

    Against MikroTik RouterOS, OPNsense wins on security features and how easily you can bolt on extra services - and no offense to the Mikrotik crowd, but OPNsense is just plain easier to configure. OpenWrt, meanwhile, is really built for home routers and is honestly closer to "an OS for aging router hardware" than a serious platform - OPNsense, by contrast, happily runs on dedicated network appliances just as well as on ordinary x86 boxes and VMs.

    And compared to rolling your own router on Linux, OPNsense saves you from having to bolt together a firewall, DHCP, DNS, VPN, and monitoring by hand. It's all baked into one platform, accessible from a single web interface.

    What You'd Actually Use It For

    OPNsense fits just as well in a home network as it does in small-to-medium business infrastructure. The usual use cases:

    • sharing one internet connection across multiple networks and VLANs;

    • setting firewall rules and segmenting the network;

    • running VPN servers and clients (WireGuard, OpenVPN, IPsec);

    • handling DHCP and DNS;

    • publishing internal services through a reverse proxy;

    • locking things down with IDS/IPS, GeoIP filtering, and other security tools;

    • keeping an eye on network activity and digging through event logs;

    • setting up high availability (HA) and redundant network infrastructure.

    OPNsense on a Home Lab

    If you're running a homelab, OPNsense can easily become the centerpiece of your network - it lets you build something that looks and behaves a lot like a corporate setup, minus the expensive gear and the CCNA.

    Typical homelab use: separate VLANs for servers, workstations, IoT junk, and guests; secure remote access over VPN; publishing services to the internet (there's a Caddy reverse-proxy plugin for that); firewalling between segments; and having one place to manage network security instead of five.

    Since it virtualizes well, OPNsense runs great in Proxmox VE and other hypervisors - so you don't necessarily need a dedicated box for it. That said, for max performance and reliability, a lot of people still like to put it on a small dedicated mini-PC with a couple of NICs.

    Note

    In the video linked above, I set everything up on a mini-PC with two physical NICs, so that's the configuration this article follows for installation and initial setup. Everything past that point applies regardless of whether you're running virtualized or on bare metal.

    Installing OPNsense

    Picking an Installation Image

    First, grab the installer image from the project's official site. There are a bunch of options listed, but picking the right one boils down to one question: where is this going to run?

    Installing on a physical box or mini-PC with a monitor and keyboard hooked up? Grab the VGA image - that's what I use in this article.

    The DVD image is aimed at virtual machines and works fine for Proxmox VE, VMware, Hyper-V, and friends.

    Got a serial console, managing things over a COM port? That's the Serial image - more common on industrial gear and certain networking appliances.

    There's also a Nano image on the downloads page, but you'll almost never need it - the devs point everyone toward a normal install with VGA, DVD, or Serial.

    Making a Bootable USB Drive

    Once you've downloaded it, flash the image onto a USB stick with Rufus, balenaEtcher, or whatever else you like for writing bootable images.

    When it's done, plug the drive into the machine you're installing on and pick it as the boot device from BIOS/UEFI.

    Running Through the Installer

    I'm skipping screenshots here to keep the article from ballooning any further.

    • Don't press any key when the Configuration Importer prompt appears.
    • When prompted for Manual Interface Assignment, press any key. I prefer to configure interfaces manually rather than use automatic configuration.
    • Press Enter to skip LAGG configuration.
    • Press Enter to skip VLAN creation (we'll configure them later through the web interface).
    • Enter igc0 as the WAN interface name.
    • Enter igc1 as the LAN interface name.
    • When prompted for an Optional Interface Name, press Enter to skip this step (we'll configure additional interfaces later).
    • Press Y, then Enter to continue.
    • At the login prompt, enter the username installer and password opnsense to begin the installation.
    • Press Enter to use the default keyboard layout (if you're using a US keyboard; otherwise select the appropriate option).

    Next up, the installer asks you to pick a file system - ZFS or UFS.

    UFS is the classic FreeBSD file system. It's lighter on resources and does the job for most home routers, but it's more "brittle" than ZFS.

    ZFS brings extras like data-integrity checking, snapshots, and much more flexible storage management - at the cost of wanting more RAM and CPU.

    For a homelab and most modern mini-PCs, I'd go with ZFS, especially if you're installing to an SSD and have at least 8 GB of RAM to spare. If you're running OPNsense as a virtual router though, keep in mind that stacking ZFS on top of ZFS isn't exactly a great idea - either way, the right filesystem really depends on your specific setup.

    Warning

    Skip the cheap no-name SSDs and NVMe drives here, especially if you're pairing them with ZFS. OPNsense writes a ton of logs as a firewall, and ZFS writes plenty of its own on top - budget drives under that kind of sustained write load tend to die fast.

    Once you've picked a filesystem, you'll select the drive to install onto. Double- and triple-check you've picked the right disk before confirming - everything on it gets wiped.

    When the file copy wraps up, the installer will ask you to set a root password. Do it right then and there, so you're not still running the default password after your first boot.

    Initial Setup

    Once OPNsense reboots after the install, it drops you into a console menu right on the attached monitor - that's also where you'll see whatever IP address it handed the LAN interface (by default that's 192.168.1.1/24, and OPNsense starts acting as a DHCP server for LAN the moment the install finishes). Everything from here on happens in the web UI - we're done with the console.

    Logging into the web UI for the first time

    Plug your laptop into the LAN port (directly, or through a switch) - it should grab an address over DHCP automatically - then open https://192.168.1.1 in a browser (or whatever address the console showed you).

    Your browser is going to throw a certificate warning right away - that's expected, it's a self-signed cert. I walked through swapping it for a real Let's Encrypt cert in my Proxmox ACME article - OPNsense has its own built-in ACME client too, and the concept is identical, but that's a separate rabbit hole. For now, just click through the warning.

    Log in as root with the password you set at the very end of the installer.

    Running through the Setup Wizard

    The first time you log in, OPNsense offers to walk you through its Setup Wizard. It's entirely optional - you can close it and configure everything by hand through the individual menus instead - but on a brand-new box it's the fastest way to get the basics out of the way. Here's what each screen does:

    1. General Information - set the Hostname (say, opnsense) and Domain (your real domain, or a placeholder like home.arpa if you don't have one handy). Together they form the box's full name (opnsense.stilicho.ru), which later shows up in certificates, DHCP leases, and logs.
    2. Time Server Information - your time zone and an NTP server. The default NTP pool is fine unless you have a reason to point at something else - accurate time matters a lot here, for certs, logs, and IDS/IPS working correctly.
    3. Configure WAN Interface - this re-asks the same WAN questions (DHCP/Static/PPPoE) you already answered in the console installer. If WAN's already up and working, just click through this screen without touching anything. Worth noting: two checkboxes further down, Block private networks and Block bogon networks - leave both enabled on your internet-facing interface. They drop packets carrying private or unallocated ("bogon") source addresses, which have no business showing up on WAN in the first place, and that alone quietly cuts a good chunk of noise out of your firewall logs.
    4. Configure LAN Interface - the IP and subnet for LAN. The default (192.168.1.1/24) is fine to keep, or change it now to whatever you'd rather use - just know that changing it will drop your current browser session, and you'll need to reconnect at the new address.
    5. Set the root password - reset it here if you want, or just skip past it.
    6. Reloading package configuration - the wizard applies everything you entered; if you changed the LAN subnet in step 4, the address in your browser's URL bar is about to change out from under you.
    Note

    You can re-run the wizard any time from System → Wizard - handy if you want to start over from scratch after a factory reset.

    Checking for updates

    Right after the wizard, it's worth checking whether anything's shipped since the install image was built. Head to System → Firmware → Status and hit Check for updates. If there's anything newer, switch to the Updates tab and click Update (a major version jump, say from 25.x to 26.x, will ask you to confirm and may reboot once or twice on its own).

    Tip

    While you're in there, take a look at System → Firmware → Plugins too - the official plugin list includes os-crowdsec and the Caddy reverse-proxy plugin, both of which come up later in this article. You don't need to install either one right now, but it's good to know they're sitting right there instead of hunting for them online as if they were third-party add-ons.

    General settings (System → Settings → General)

    A few fields here are worth double-checking even if you already ran the wizard:

    • Hostname / Domain - same values you set in the wizard; you can rename the box here later if you change your mind.
    • DNS servers - fine to leave blank or at the defaults for now. Once you get to the Unbound DNS section below, leaving this field empty becomes a deliberate choice rather than an oversight - I explain why right there.
    • DNS server options - uncheck Allow DNS server list to be overridden by DHCP/PPP on WAN if you're planning to run your own resolver (Unbound or Dnsmasq) - otherwise your ISP's DNS servers can quietly sneak back into the config on top of yours.
    • Language and Top navigation - purely cosmetic. I leave the UI in English, since every doc page and forum post I need to cross-reference is in English too, and it's a lot less friction matching what's on screen to what you're reading online.

    Web UI and SSH access

    Over in System → Settings → Administration, a few settings are worth locking down early:

    • TCP port - the web UI's port, 443 by default. If you're planning to also run OPNsense as a reverse proxy on port 443 for internal services down the line, it'll collide with the admin UI on that same port - move the admin port to something non-standard now (8443, say) and save yourself the headache later.
    • Listen Interfaces - leave it blank and the web UI listens on every interface, WAN included. You almost never need admin access from outside your own network - restrict this explicitly to LAN (and a management VLAN, if you're running one), so the web UI simply isn't reachable from the internet, regardless of what your firewall rules say.
    • Secure Shell, further down the same page - turns on SSH access to the OPNsense shell. It's off by default; only flip it on if you actually need it (troubleshooting CrowdSec later in this article is a good example), and when you do, move it off port 22 and lock it down to specific source IPs with a firewall rule.

    That's the box squared away - from here we'll get into DNS, VLANs, firewall rules, and locking the whole thing down against attacks.

    Setting Up Unbound DNS

    Unbound is a validating, recursive, caching DNS resolver built for speed and security. It's open-source, BSD-licensed, built by NLnet Labs, and it's the thing quietly resolving domain names to IP addresses behind the scenes on a huge number of platforms. Sysadmins, ISPs, and privacy nerds all lean on it heavily, and it plays nicely with OPNsense, pfSense, FreeBSD, Linux, macOS, and pretty much any other Unix-like OS.

    I'm only going to cover the core Unbound features here, as they apply inside OPNsense.

    What Unbound Brings to the Table

    Unbound supports DNSSEC (Domain Name System Security Extensions), which vouches for the authenticity and integrity of DNS data and protects you from things like DNS spoofing or cache poisoning. It can also do recursive queries and cache the results, which speeds up repeat lookups noticeably.

    A quick rundown of what Unbound gives you:

    • Efficiency and lightness: designed to use minimal resources.
    • Configuration flexibility: supports a wide range of configuration options for complex, advanced setups.
    • DNS-over-TLS/HTTPS: encrypts DNS queries to improve privacy.
    • IPv6 support: fully compatible with modern internet protocols.
    • Access control: lets you configure which clients are allowed to make DNS queries to the server.

    Setting Up DNS over TLS

    DNS over TLS (DoT) encrypts your DNS queries so they can't be casually snooped on or tampered with in transit. OPNsense lets you turn this on using the built-in Unbound resolver.

    What follows is the short version - for the full walkthrough with all the details, see my dedicated articles on DNS over TLS in OPNsense and its alternative, DNS over HTTPS in OPNsense via DNSCrypt-proxy.

    How It Works

    By default, DNS queries fly across the network completely in the clear. Your ISP - or anyone else in the middle - can watch UDP/TCP traffic on port 53 and see exactly what domains you're resolving, or worse, mess with the answers. That's the whole reason to encrypt DNS in the first place. DNS over TLS (DoT) uses TLS to wrap your DNS traffic and is one of the more widely adopted ways to do this. The point is simple: more privacy, more security. A few concrete benefits:

    • Attackers can't quietly tamper with your DNS responses.
    • It kills man-in-the-middle attacks - the kind where your request gets hijacked and redirected to a phishing page.
    • It's supposed to stop eavesdropping too, though let's be honest, for a home network that benefit is mostly theoretical.

    Turning On DoT in OPNsense

    Here's how to get DoT configured and running on your OPNsense box:

    1. Go to "Services" → "Unbound DNS" → "DNS over TLS" in the OPNsense web interface.

    1. Click the "+" Add button in the bottom-right corner of the panel.
    2. Make sure the "Enabled" option is checked.
    3. You can leave the Domain field empty - that way every query gets sent to the server you specify below. Fill in a domain name instead, and only queries for that specific domain get routed to this server.
    4. Enter the IP address of the DNS server to forward all queries to, for example 8.8.8.8.
    5. Set the server port for DoT to 853.
    6. Enter the DNS server's common name (for example, dns.google.com) in the Verify CN field so its TLS certificate can be validated. Without certificate verification, DoT is wide open to man-in-the-middle attacks. You can leave this blank to accept self-signed certs, but doing so basically defeats the whole point of this exercise.

    1. Click "Save".
    2. You can add an IPv6 DNS server as a secondary resolver.
    3. Click "Apply" to activate the settings.

    In the end you'll get something like this.

    Making DNS and DHCP Play Along

    Just enabling DoT isn't enough - you need to force every client on the network to actually use those DoT servers, which means touching your DNS and DHCP settings too:

    1. Go to System → Settings → General in the left-hand menu.
    2. Make sure every DNS server field is empty. That keeps DNS traffic routed back through the router itself.
    3. Uncheck "Allow DNS server list to be overridden by DHCP/PPP on WAN." Leave it checked, and the DNS servers your ISP hands out over DHCP/PPP on the WAN side will quietly take over as the DNS provider - which defeats everything you just set up.

    For a properly locked-down setup, it's worth adding a firewall rule that blocks outbound DNS traffic on port 53 entirely, so nothing can bypass the local resolver - Unbound itself talks to upstream servers over DNS over TLS on port 853, not 53. If some client insists on querying an outside name server directly, a NAT redirect rule can bounce those queries to 127.0.0.1:53, the local Unbound instance, guaranteeing they go out over TLS regardless.

    You'll need to look up the CN domain used for DoT for whichever provider you're pointing at.

    For Quad9, that's dns.quad9.net.

    Checking the Unbound Logs

    Worth double-checking that queries are actually going out over DoT on port 853, rather than assuming it just works.

    Here's how:

    1. Go to Services → Unbound DNS → Advanced.

    2. Scroll down to the Logging Settings section.

    3. Enable the Log Queries option.

      Unbound will start logging every single query it handles - timestamp, client IP, domain requested, query type and class, all of it.

      Note. Logging every DNS query will noticeably eat into resolver performance, so treat this as a diagnostic tool - flip it back off once you've confirmed things are working.

    4. Set Log Level Verbosity to Level 2 - that's detailed enough to actually diagnose what DoT is doing.

    5. Hit Apply.

    6. Head over to Services → Unbound DNS → Log File.

    7. Search for 853.

    If DoT is working, you'll see log entries showing Unbound talking to your configured resolver over port 853 - confirmation that queries are going out encrypted instead of over plain old port 53.

    Setting Up the DHCP Server

    ISC (Internet Systems Consortium) built and maintained the open-source ISC DHCP server for years - but active development on it stopped back in October 2022.

    Its official successor is Kea DHCP, also from ISC.

    Through OPNsense 25.7, ISC DHCP was the default. Starting with 25.7, that job passed to Dnsmasq DNS and DHCP instead, since it's lightweight and a good fit for small networks. OPNsense still ships Kea DHCP too, so you're free to pick whichever suits your setup better.

    I've got a separate article on migrating from ISC to KEA, but here I'll just walk through the Dnsmasq side of things.

    Note

    Some parts of the video (and this article) are optional - not everyone needs static DHCP reservations or domain/host overrides.

    Dnsmasq or Kea?

    The choice here comes down less to raw performance and more to what you're actually trying to do.

    Dnsmasq DHCP

    For most home users and small homelabs, Dnsmasq is the way to go - which is exactly why it's the default now.

    Dnsmasq fits well if:

    • your home network or homelab consists of several VLANs and doesn't need complex DHCP infrastructure;

    • you want to use Dnsmasq not just as a DHCP server, but also as a DNS forwarder instead of Unbound DNS;

    • you need device names obtained via DHCP to automatically register in the local DNS server;

    • you plan to use OPNsense's special DNS aliases to block access to certain domains.

    Kea DHCP

    Kea DHCP is ISC DHCP's modern successor, aimed at meatier use cases.

    Reach for it if:

    • you need DHCP high availability;

    • your network has fancier routers that need IPv6 prefix delegation.

    And What About DNS?

    Beyond DHCP, you've also got a DNS service to pick. OPNsense gives you two: Dnsmasq DNS and Unbound DNS.

    Even though Dnsmasq took over as the default DHCP server, Unbound is still the primary DNS server here. Each has its own strengths.

    Dnsmasq DNS

    Dnsmasq makes sense when:

    • you want to use DHCP and DNS within a single service;

    • you need support for OPNsense DNS aliases, which automatically resolve domain names to IP addresses for use in firewall rules;

    • you need the simplest possible DNS configuration without a lot of extra settings.

    That said, Dnsmasq is noticeably less capable than Unbound overall - fewer configuration knobs, and much thinner logging/diagnostics for DNS queries.

    Unbound DNS

    Unbound is OPNsense's default DNS server, and the one I'd recommend to most people.

    What it brings to the table:

    • it's a full recursive DNS resolver that can query the root DNS servers directly, without relying on public DNS providers;

    • it supports DNS Block Lists (DNSBL), letting you block ads, trackers, and malicious domains, similar to Pi-hole;

    • it supports DNS over TLS (DoT), so DNS queries can be sent encrypted through trusted DNS servers such as Cloudflare or Quad9;

    • it provides detailed statistics and reports on DNS activity in the Reporting section, which significantly simplifies diagnostics and query analysis.

    One gotcha: once you turn on DNS over TLS, Unbound stops acting as a recursive resolver and instead just forwards everything to whatever external server you picked, over an encrypted connection.

    Running Dnsmasq and Unbound Side by Side

    Sometimes it's worth running both at once.

    For instance: Dnsmasq handles DHCP while Unbound stays the primary DNS server. Clients keep sending their DNS queries to Unbound as usual, and anything asking for a local hostname gets automatically forwarded over to Dnsmasq, which already knows about every device that grabbed an address via DHCP.

    That gets you the best of both worlds - Unbound's more advanced feature set, plus automatic name resolution for everything on the local network.

    Setting Up DHCP Ranges

    With the core settings out of the way, you now need a DHCP pool for every interface that's going to hand out addresses.

    Go to:

    Services → Dnsmasq DNS & DHCP → DHCP Ranges

    Setting Up the Firewall

    Time to cover the basics of packet filtering in OPNsense - how firewall rules get built and applied, with a few simple examples along the way.

    How the OPNsense Firewall Actually Works

    Here are the core concepts you need before any of the packet filtering stuff makes sense.

    Rules

    OPNsense runs on a Stateful Packet Filter - it decides what traffic is allowed to move between networks, and how packets get forwarded through the box.

    Firewall rules here are just security policies attached to traffic, organized per interface.

    The building blocks of a rule, below.

    Actions

    Every rule gets one of three actions.

    Pass (Allow)

    Lets the traffic through.

    Block

    Drops the traffic silently - the client gets no indication anything happened.

    This is what you want for untrusted networks, i.e. the internet.

    Reject

    Drops the traffic and tells the client about it.

    Only works for TCP and UDP:

    • TCP gets an RST (Reset) packet;
    • UDP gets an ICMP Destination Unreachable back.
    Note

    Note On internal networks, Reject is usually the friendlier choice - the client finds out immediately instead of sitting around waiting for a timeout. On untrusted networks like the internet, go with Block instead - no point handing a would-be attacker any extra information about how your firewall behaves.

    The "Allow All" Rule

    Once you've finished the initial LAN/WAN setup, OPNsense quietly drops in a few default rules for you:

    • an anti-lockout rule (Web Administration Anti-Lockout Rule);
    • an Allow All rule for IPv4;
    • an Allow All rule for IPv6.

    Two things these rules do for you:

    • keep you from accidentally locking yourself out of the OPNsense web UI;
    • give LAN devices full access to the internet and anything else behind the firewall.

    So anything plugged straight into the router - or into a switch hanging off it - gets online immediately, no extra rule-writing required.

    Delete or disable Allow All, though, and all outbound LAN traffic gets blocked. The one thing that keeps working is access to OPNsense's own web UI.

    Why You'd Turn Off Anti-Lockout on a Corporate Network

    Anti-Lockout is great for home use, but it's a liability in a corporate setting.

    The problem: it lets any device on the LAN reach the firewall's management interfaces, including:

    • the Web GUI;
    • the SSH console.

    Not exactly a comforting thought from a security standpoint - that's a straight line to compromise or data leaks.

    So on a corporate network, you'd want to:

    1. turn off Anti-Lockout;
    2. write your own rule that only lets admins or trusted devices in.

    Looking at the Default Rules

    Want to see what OPNsense created automatically?

    1. Go to Firewall → Rules → LAN.
    2. At the top of the rule list, click the dropdown icon next to Automatically generated rules.

    That'll show you the automatically created rules, including:

    • Default Anti-Lockout Rule;
    • Allow LAN to Any.

    The Order OPNsense Checks Rules In

    When a packet shows up, OPNsense walks through rules in this order:

    1. Floating Rules;
    2. Interface Groups (group-level rules);
    3. Interface Rules (rules on individual interfaces).

    The auto-generated system rules typically land at the front of that queue.

    Quick, and How It Changes Rule Matching

    Most rules ship with Quick turned on by default.

    With Quick enabled, it's simple:

    Note

    First Match Wins.

    The moment a packet matches a rule:

    • checking stops right there;
    • everything after it gets ignored.

    Turn Quick off, and the logic flips:

    Note

    Last Match Wins.

    You'll rarely need this mode - it's really only for specialized filtering policies.

    The standard Default Deny rule is a good example of exactly this mechanism: no matching rule means the packet gets dropped.

    Why Order Matters So Much

    Rules get evaluated top to bottom, full stop.

    Which means where you put a rule directly decides what happens to matching traffic.

    The instant a packet hits a rule -

    • Pass;
    • Block;
    • Reject,

    processing stops right there.

    That's the whole reason behind the standard advice:

    • specific rules go near the top;
    • broad, catch-all ones go near the bottom.

    A typical layout:

    1. let LAN users through on HTTP and HTTPS only;
    2. then allow DNS;
    3. add whatever else you actually need;
    4. finish with a Deny All or Allow All rule to mop up anything left over.

    Do it this way and the config stays readable, and your security posture is noticeably better for it.

    Traffic Direction

    Rules apply in one of two directions:

    • Incoming (In);
    • Outgoing (Out).

    OPNsense defaults to filtering incoming traffic (In).

    Which means: build the rule on whichever interface the packet arrives on.

    For Example

    Say you want to let HTTPS (port 443) traffic from the internet reach an internal web server. The rule goes on the WAN interface, since that's where packets from the outside world first hit OPNsense. From there it'll allow incoming TCP 443 connections to your server.

    The idea is to only let clients talk to:

    • OPNsense's own built-in DNS server;

    • your own local DNS server;

    • or a trusted external DNS service that does filtering.

    Destination NAT (Port Forward)

    What Port Forwarding Actually Does

    When several devices on a local network hide behind a single external IP, every incoming connection from the internet lands on that same address.

    Without extra config, OPNsense has no idea which internal device an incoming connection is actually meant for - so it just gets rejected.

    Destination NAT (DNAT), better known as Port Forward, is the fix.

    The classic case: publishing an internal web server. To make it reachable, forward incoming connections on:

    • 80/TCP (HTTP);
    • 443/TCP (HTTPS).

    Where to Configure This

    Head to:

    Firewall → NAT → Destination NAT (Port Forward)

    You'll see every existing DNAT rule here, plus the usual create/edit/delete controls.

    The Core DNAT Fields

    Here's what you'll be filling in when creating a new rule.

    Parameter Description
    Disabled Disables the rule without deleting it. While this option is enabled, the rule doesn't apply.
    Sequence Sets where the rule falls in the processing order - OPNsense works through rules top to bottom.
    Categories Lets you assign the rule one or more categories for easier organization and filtering.
    Description A free-text description of the rule. Give it a clear name so you can tell what it's for at a glance later.

    Interface Fields

    You'll also need to say which interface and traffic type the rule targets.

    Parameter Description
    Interface Which interface (or interfaces) receive the incoming traffic. Usually WAN, since that's what you're publishing services on.
    Version The IP protocol version the rule applies to: IPv4, IPv6, or both at once.
    Protocol The protocol the rule has to match. Most of the time that's TCP, UDP, or a TCP/UDP combo, but other protocols are supported too.

    Getting the Source Fields Right

    Filtering and NAT rules both hinge on defining the source correctly.

    Parameter Description
    Invert Source Flips the source match: instead of matching the specified range, the rule matches everything except it. For example, "everything except 192.168.1.0/24".
    Source Address Specifies the source network, IP address, or alias the traffic should come from. You can use individual hosts, entire networks, or groups.
    Source Port Defines the source port or port range. Rarely used, since client ports are usually assigned dynamically - but it can come in handy for specialized filtering.

    And the Destination Fields

    Just as important - nailing down exactly where the traffic is going. That's what the Destination fields handle.

    Parameter Description
    Invert Destination Flips the destination match: instead of the specified address or network, the rule applies to everything except it.
    Destination Address The IP address, network, or alias traffic should be directed to. Can include individual hosts or address groups.
    Destination Port The destination port or port range. Used to filter specific services (for example, HTTP, HTTPS, DNS, etc.).

    Redirect / Translation Fields

    These decide exactly where incoming traffic actually ends up once the rule fires.

    💡 How It Works

    NAT translation swaps the original external destination (say, your firewall's public IP) for the internal server's address.

    For example:

    • external IP: 203.0.113.10:443

    • internal server: 192.168.1.50:443

    Once the rule's live, the connection gets redirected to the internal host automatically.

    Redirection Fields

    Parameter Description
    Redirect Target IP The internal IP address incoming traffic will be redirected to. Usually a server on the local network (LAN or DMZ).
    Redirect Target Port The port on the internal host that the connection will be redirected to. It can match the external port or differ from it (for example, 80 → 8080).
    Pool Options Controls how traffic gets spread across multiple internal IPs - load balancing, or picking a target via a specific algorithm.

    A Few More DNAT Options

    There are also some extra knobs governing how the rule behaves, syncs, and interacts with the rest of your firewall rules.

    Options Fields
    Parameter Description
    No XMLRPC Sync Excludes this rule from synchronization with HA (High Availability) partners. Used in clusters where not all NAT rules should be copied to the secondary node.
    NAT Reflection Controls NAT reflection (hairpin NAT) mode. Lets internal clients reach services via the external IP address. Can be enabled, disabled, or inherit the global setting.
    Set Tag Assigns a tag to packets matching this NAT rule. Used for further processing by other firewall rules.
    Match Tag Lets the rule apply only to packets that already carry a specific tag. Used for complex routing and filtering scenarios.

    Firewall Rule (Auto-Generating Rules from NAT)

    OPNsense can spin up matching firewall rules automatically based on your NAT config.

    Your options:

    Option Description
    Manual (recommended) The administrator manually creates the firewall rules. This is the most flexible and recommended option.
    Pass (auto rule) Automatically allows traffic matching the NAT rule. These rules don't appear on the Firewall Rules tab.
    Generate Interface Rules Automatically creates rules on the interface, which can then be overridden by higher-priority rules.

    A Word of Caution

    A few things worth keeping in mind if you go with auto-generated rules:

    • the NAT rule and firewall rule need to agree on the same target address;

    • higher-priority interface rules can still override the auto-generated ones;

    • for anything complex, manual rule management will save you from weird conflicts and mystery blocks down the line.

    Firewall Rules for Blocking Outbound Connections

    By default, CrowdSec in OPNsense only blocks incoming connections from known-bad IPs. It doesn't cover the reverse case - something inside your network reaching out to one of those addresses on its own.

    Think:

    • a compromised host on the LAN;
    • a malicious script or container;
    • someone accidentally running something sketchy.

    In any of these, the connection gets through unless you've separately blocked outbound traffic to those known-bad IPs.

    Floating Rules are the tool for this - they let you apply a single rule across multiple interfaces at once (LAN/VLAN).

    Creating the Floating Rule

    Go to:

    Firewall → Rules → Floating

    Click Add (+) top-right.

    Set it up like so:

    Parameter Value
    Action Block
    Interface LAN (or the relevant VLANs/interfaces)
    Direction In
    Protocol Any
    Destination crowdsec_blacklists
    Log Enabled
    Description Block access to CrowdSec blacklist
    IPv4 and IPv6

    Running IPv6? You'll need a second rule for that traffic specifically.

    OPNsense won't always automatically apply one rule to both stacks, so it's cleaner to split them:

    • one rule for IPv4
    • one for IPv6
    Apply It

    Once both rules exist, hit:

    Apply Changes

    From here on, anything inside your network trying to reach an IP on the CrowdSec blacklist gets stopped at the firewall.

    Why This Actually Matters

    This closes a real gap in coverage:

    • CrowdSec handles incoming traffic (internet → LAN)
    • Floating rules handle outgoing traffic (LAN → internet)

    Together they cut down not just external attacks, but the blast radius if something inside your network does get compromised.

    Warning

    Which FireHOL level should you choose? FireHOL aggregates dozens of different threat-intelligence sources and provides several blocking levels.

    • firehol_level1 - the most conservative list. It only includes IP addresses with a high threat reputation, so the risk of false positives is minimal. This is the level most users should go with.
    • firehol_level2 - includes more addresses and provides more aggressive filtering, but the chance of blocking legitimate resources goes up.
    • firehol_level3 - the strictest level. It combines a large number of sources and can trigger false positives, so it should only be used if you understand the potential consequences.
    • firehol_abusers_1d - a list of IP addresses seen engaging in suspicious activity over the last 24 hours. It's updated continuously and helps quickly block new attack sources.
    • For a home network or small infrastructure, firehol_level1 is usually enough. If you regularly see a lot of scans or password brute-force attempts, you can additionally add firehol_abusers_1d.
    • Level2 and level3 are best enabled only after evaluating the possible consequences and monitoring the firewall logs.

    Split DNS

    Split DNS in a Nutshell

    The idea: the same domain (say, stilicho.ru) resolves to different answers depending on whether the client asking is on your internal network (LAN) or out on the internet.

    Split DNS gives internal and external users different answers to the same query, so local requests to your own server never need to detour through the router. A few reasons this is worth doing:

    • Faster, since the router's no longer in the path.
    • A reverse proxy can cleanly tell internal and external requests apart and allow/deny accordingly, since NAT isn't in the mix.
    • Everything keeps working even with no internet access.
    • Still works even if your upstream DNS (ISP, Google, OpenDNS, whatever) goes down.

    What You'll Need

    • An internal reverse proxy listening on port 80/443.
    • An internal DNS resolver that can do overrides, or host full DNS zones.

    A Typical DNS Setup

    For this example, domain.com is your domain, and 10.10.10.10 is your reverse proxy.

    Go to Services > Unbound DNS > Overrides > Host Overrides > Add:

    • Host: *
    • Domain: stilicho.ru
    • Type: A or AAAA
    • IP: 10.10.10.10
